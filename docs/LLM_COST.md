# Section C：剧情模式与大模型 Token 评估

> 历史评估：从 v0.8 起，当前主版本已撤下剧情状态机，也不接入大模型。本页仅保留未来重新评估时的成本与安全边界，不描述当前游戏功能。

## 结论

v0.5 **不把大模型接入公开试玩版**。先发布本地剧情状态机：

- 运行时 Token 消耗为 0；
- 不需要 API Key、账号或登录；
- 对话断网仍可用；
- 剧情只读取“刚才在商场发生了什么、购买轮次、刮票/验票状态”，不能读取或修改未刮彩票结果。

原因不只是费用。公开网页不能安全地内置模型 API Key；若直接从浏览器调用，密钥会被访客获取。正式接入至少需要一个受控后端、用量限制、内容边界、失败回退和隐私说明。

## 每局 Token 预算估算

假设一次游玩与老板发生 8–14 轮短对话，每轮模型输出 50–120 个中文 Token。

### 方案一：每轮携带完整历史

| 项目 | 单局估算 |
|---|---:|
| 系统规则与店况 | 600–1,000 输入 Token |
| 随轮次增长的对话历史 | 8,000–18,000 输入 Token |
| 模型回复 | 600–1,600 输出 Token |
| 合计 | 约 9,200–20,600 Token |

### 方案二：本地状态机 + 压缩摘要

每次只发送当前店况、最近两轮对话和约 200 Token 的状态摘要。

| 项目 | 单局估算 |
|---|---:|
| 固定规则与状态摘要 | 4,800–8,400 输入 Token |
| 模型回复 | 600–1,400 输出 Token |
| 合计 | 约 5,400–9,800 Token |

若朋友反复游玩 100 局，优化方案仍大约需要 54–98 万 Token。具体货币费用取决于未来选用模型的实时价格，因此不在代码中写死。

## 将来允许接入时的硬边界

1. 大模型只能生成闲聊文本，不能决定奖项、改预算、操作兑奖或重新抽票。
2. 彩票整本和单张结果必须在对话前由本地确定，并且不发送给模型。
3. 每局设置输入、输出、轮数和人民币费用上限；超限自动回退本地对白。
4. 不把聊天记录用于跨玩家画像；默认不长期保存。
5. API Key 只保存在托管端环境变量中，绝不下发到浏览器。
6. 模型失败、限流或断网时，游戏闭环仍能完整运行。

## v0.5 的本地剧情结构

- 玩家在预算页选择“逛街剧情”或“快速进店”。
- 剧情模式随机提供三段商场事件，例如取奶茶、抓娃娃机、寄存购物袋、朋友催促、排队验票和雨天广播。
- 选择结果会进入店况和老板开场白。
- 后续购买与验票会推进剧情段数，但不重新生成彩票。
